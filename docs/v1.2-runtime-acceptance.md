# v1.2 Agent Optimizer — Runtime Acceptance

匿名化的 v1.2 Emergency-MVP runtime 驗收紀錄。本文件不含 API key、Authorization header、
完整 prompt、文件全文或任何私人資料；Run ID 只保留短碼供追溯。

## Purpose

驗證 v1.2 有界 LLM-guided 檢索最佳化 Agent 在**真實環境**能端到端跑通：Fake Planner 兩輪
回饋迴圈，以及一次真實 OpenAI-compatible Provider 的單輪執行；並確認整個過程不 Apply、不
Publish Dataset、不切換 alias、不觸碰正式 `factory_knowledge`、不外洩 secret，且結束後無殘留
測試 collection。本輪**不要求候選指標改善**——證明的是迴圈與拒絕行為正確，而非品質提升。

## Environment Isolation

- 使用**獨立、ephemeral 的 Qdrant** 容器（對外 port 6350，映射容器內 6333，**不掛任何 volume**）
  作為測試實例，CLI 以 `--qdrant-url` 明確指向它。
- 正式 compose Qdrant 容器全程處於停止狀態，正式 volume `factory-rag-assistant_qdrant_data`
  從未被掛載；正式 `factory_knowledge`（10 points、無 alias）因此不可能被觸碰。
- 測試實例啟動前為空：0 collections、0 aliases、無 `factory_knowledge`。
- 驗收結束後測試容器已移除，正式容器與正式 volume 維持原狀。

## Fake Two-round Run

- Planner：`fake`（不呼叫任何 Provider）；`--max-rounds 2`。
- Baseline：真實建立並在 tune／validation 上實算指標（示範資料上 accuracy＝1.0、mrr＝1.0）。
- 兩輪各產生一個真實 Candidate Trial（Round 1 提議 `top_k 5→6`、Round 2 `top_k 5→4`），
  candidate 的 config hash 兩輪不同。
- 兩輪皆產生 Probe Questions，且**同一組 probe 在 Parent 與 Candidate 上分別執行**並產生
  Parent／Candidate Probe Comparison。
- Round 2 的受控 context 帶入 Round 1 的 probe comparison（context hash 兩輪不同，回饋確實進入
  下一輪）。
- 兩輪候選皆由 deterministic gate 拒絕（見下方「Promotion 判定用語」）。
- Stop reason：`max_consecutive_rejections`；Recommendation Eligibility：`not_evaluated`；
  Residual collections：無。

## Real LLM One-round Run

- Planner：`llm`（必須明確指定；不會因環境存在金鑰就自動呼叫）；`--max-rounds 1`。
- Provider type：OpenAI-compatible；Model：`llama-3.3-70b-versatile`。
- 真實 Provider 收到受控 context，回傳可解析為 Proposal Schema 的 JSON。
- Validator 接受該合法 Proposal（單一變更 `score_threshold 0.55 → 0.50`，非 parent-identical、
  非重複）。
- Candidate Trial 真實執行；3 個 probe 於 Parent 與 Candidate 上比較並產生 comparison。
- Official Metrics 與 Constraints 計算完成（constraint feasible，pass_count＝2）。
- Promotion Decision 產生：候選被 deterministic gate 拒絕（品質指標與 Parent 相同）。
- Agent DB 寫入匿名化 Audit（無 raw response、無 token usage、無 secret）。
- 全程無 Apply、無 Publish、無 alias 切換、無殘留 collection。
- 結果為 `rejected` — 屬允許結果；候選被拒絕是有效結果。

### Promotion 判定用語

CLI／Audit 內原始 promotion reason 字串為：

```text
not_better_than_parent (decided_by=config_hash)
```

較清楚的解讀（`config_hash` 只是穩定排序的最終 tiebreak，**不是品質指標**）：

```text
quality_metrics_tied
stable_order_tiebreak=config_hash
candidate_not_promoted
```

亦即：候選在所有實質品質指標上與 Parent 打平，comparator 落到最後一個穩定排序鍵
（`config_hash`）才分出順序，因此**不判定為勝出**、不升級。核心 comparator 邏輯本輪未修改，
此處僅補充較不易誤解的說明。

## Runtime Bug Found

真實 LLM 首次執行時，即使是能力足夠的 Provider 也無法產生任何合法 Proposal，導致 Candidate
Trial 與 Probe **從未執行**（命中「invalid config／trial 未執行／probe 未執行」）。根因全在
**受控 context／LLM 指令**（非 Validator、非核心政策）：

1. Prompt 從未明確告知 `max_parameter_changes`（只藏在 context 的 budget 物件內）。LLM 因此
   切換 chunk strategy，而切換 strategy 在差異計算上會一次改動多個欄位，必然超過上限 2。
2. 送給 LLM 的 `current_config` 含**不可提案**的 canonical 版本欄位（`prefix_format_version`／
   `ranking_version`）；照抄整個 config 會觸發 Validator 白名單錯誤。
3. `output_schema` 範例誘導 LLM 一律填入 `anchor_text_suggestions`，而 anchor 必須是所綁定
   segment 的逐字子字串，否則被拒——LLM 因此臆造不存在的 anchor。

## Fix Applied

只修正受控 context／LLM 指令，**Validator 與安全政策完全未放寬**（commit
`fix: complete v1.2 runtime acceptance`）：

- 明確 hard constraints：在送給 LLM 的訊息中新增醒目的頂層物件，含 `max_parameter_changes`、
  `max_probe_questions`、`available_segment_ids`，並在 System Prompt 加入對應規則。
- `editable_current_config`：把 `current_config` 過濾為**僅含 Validator 白名單欄位**的現值供
  LLM 逐欄位照抄；欄位集合與 Validator 完全一致。
- `available_segment_ids`：明確列出可綁定的 segment id。
- Anchor example 預設為空陣列 `[]`（空 anchor 為合法），降低 LLM 臆造 anchor 的傾向。

修正後真實 LLM **首次呼叫即產生合法 Proposal**，完整跑完 Candidate Trial → Probe →
Metrics → deterministic promotion 判定。過程中沒有任何 Proposal 被人工竄改。另補兩個
deterministic（不呼叫 LLM）回歸測試，鎖定「hard constraints 有被攤給 LLM」與「照抄
`editable_current_config` 並只改一個欄位可通過 Validator」。

## Known Limitations

- Demo baseline 已達 Accuracy／MRR＝1.0，本迴圈證明的是迴圈與拒絕行為，而非可量測的品質改善。
- 只能提出既有 whitelist 內的 chunking／retrieval 參數。
- Recommendation Eligibility 維持 `not_evaluated`：held-out test 與 recommendation lock 不在
  Emergency MVP 範圍。
- 目前只有最小 Audit；完整 resume 與報表 UI 為 deferred。
- 單一真實 provider／model 的一次執行不足以證明跨模型穩健性。
- Token usage 可能為 null，因為共用的正式 LLM client 只回傳文字。
