# v1.2.1 — Cross-Encoder Rerank: Design and Result

Canonical design document for the offline Cross-Encoder rerank capability.

**Scope up front:** this feature lives entirely in the **offline evaluation / optimizer
layer**. Production retrieval (`/api/retrieve`) is unchanged and remains dense-only. No
code under `app/` was modified at any point in v1.2.1.

- Operational runbook: [v1.2.1-rerank-runbook.md](v1.2.1-rerank-runbook.md)
- Quality evidence: [../evaluation/rerank-quality-evaluation-v1.2.1.md](../evaluation/rerank-quality-evaluation-v1.2.1.md)
- Latency evidence: [../evaluation/rerank-end-to-end-latency-v1.2.1.md](../evaluation/rerank-end-to-end-latency-v1.2.1.md)
- Prerequisite gates / provisional budget: [../evaluation/rerank-latency-baseline-v1.2.1.md](../evaluation/rerank-latency-baseline-v1.2.1.md)

## 1. Motivation

v1.1 retrieval ranks purely by bi-encoder cosine similarity, optionally adjusted by
identifier-aware boost and confusable penalty. A bi-encoder embeds the query and the chunk
*independently*, so it cannot model token-level interaction between them. Two chunks that
mention the same equipment code differ in ways a bi-encoder compresses away.

A Cross-Encoder scores the `(query, chunk)` pair jointly and can express that interaction.
The pre-registered expectation was that it would fix specific known ranking failures —
notably `eval-e102-001` and `eval-e102-confusable`, both sitting at `first_relevant_rank = 2`.

The question v1.2.1 set out to answer was deliberately narrow: **does an offline
Cross-Encoder rerank stage improve retrieval quality enough to justify its cost, on this
project's dataset and under this project's latency budget?**

---

## 2. Architecture

The rerank stage is **orthogonal to retrieval strategy**, not a third strategy. Both
`dense` and `identifier_aware` share one implementation.

```
query
  -> query embedding
  -> vector search (dense candidates [+ identifier-filtered candidates])
  -> dedup / union
  -> boost / penalty                (identifier_aware only)
  -> ADMISSION  (score_threshold, identifier_vector_floor)   ==> admitted set A
  -> W = A[:rerank_top_n]           scored by cross-encoder, reordered by raw logit
     T = A[rerank_top_n:]           NOT discarded, original relative order kept
  -> (rerank(W) ++ T)[:top_k]
```

| module | role |
| --- | --- |
| `evaluation/v11/retrieval/reranker.py` | `CrossEncoderReranker`, `NoOpReranker`, `sigmoid` |
| `evaluation/v11/retrieval/rerank_stage.py` | `apply_rerank` / `maybe_rerank` — shared by both strategies |
| `evaluation/v11/rerank_cache.py` | SQLite score cache + fingerprint-bound facade |
| `evaluation/v11/rerank_fingerprint.py` | deterministic model fingerprint + cache key |
| `evaluation/v11/real_services.py` | builds the real reranker + cache, injects via `RetrievalRequest` |

Config carries two orthogonal fields, `rerank_strategy` (`none` | `cross_encoder`) and
`rerank_top_n`. When `rerank_strategy=none` the canonical config dict emits **no** rerank
keys at all, so every pre-existing config hash, dataset and baseline stays byte-identical.

---

## 3. Admission-before-rerank invariant (H3)

**The rerank stage sits after admission and has no admission or filtering authority.**

```
For any case:   results non-empty   <=>   admitted set A non-empty
```

Admission is the safety gate v1.1 spent Slices 4 and 5 tuning. If reranking ran *before* it,
a high rerank score could rescue a chunk that failed `score_threshold`, which would destroy
the control on unanswerable false positives. Placing it after admission makes that
impossible by construction: `A` non-empty ⟹ `W` non-empty ⟹ output non-empty, and rerank
never adds or removes a candidate — it only reorders `W` and truncates to `top_k`.

`unanswerable_false_positive` is decided purely by whether the result list is empty, so the
false-positive rate is *provably* identical with rerank on and off. R3 measured exactly
that: 28/28 (arm, case) pairs consistent, 0 violations, FP rate unchanged for both
strategies.

**Adding any rerank score threshold or filter would break H3 immediately. This prohibition
is not removable.** The corollary matters: a false positive originating in admission
(as `identifier_aware` exhibits on the test split) is *structurally unfixable* by reranking
and must be addressed at the admission layer.

## 4. Raw logit / Identity activation

`sentence_transformers.CrossEncoder.predict()` applies **Sigmoid by default** when
`num_labels == 1`. This project ranks by **raw logit**, so the reranker passes
`activation_fn=torch.nn.Identity()` explicitly.

This is not a stylistic choice. Silently accepting the default would squash scores into
`[0, 1]`; the saturated ends then collapse into false ties after report rounding, and the
ranking would degrade invisibly. R0 measured raw logits in `[-10.20, +3.57]` — far outside
the unit interval.

- `ranking_score = rerank_score` (raw logit) — the sort key.
- `rerank_score_normalized = sigmoid(raw)` — **report / audit only**, never a sort or
  tie-break key.

The activation is recorded in the fingerprint, so switching to caching activated values
would change the fingerprint hash and invalidate old cache entries rather than silently
mixing two score semantics.

## 5. `RERANK_BATCH_SIZE = 1`

R0 measured a cross-batch score deviation of `4.292e-06` (~3.5× float32 ULP at that
magnitude) between batch 1, 8 and 32 — above the original `1e-6` tolerance.

Root cause was isolated, not guessed: an **identical-input control** (every pair the same,
so no length variation and therefore no padding variation) produced delta `0.0`, and
**repeat determinism** at fixed batch size produced delta `0.0`. The deviation is
padding-induced reduction-order variance in float32.

Repository Owner decision: fix `RERANK_BATCH_SIZE = 1`. Batch 1 has no padding by
construction, so padding-induced drift is identically zero — and on CPU it measured
*faster* than the originally planned batch 16 (183.8 vs 259.5 ms/pair).

Batch size is therefore a **runtime implementation constant**: not in `RetrievalConfig`,
not in the config hash, not in the cache key, not in the optimizer search space. The
cross-batch comparison was demoted from blocking gate to audit evidence; the blocking gate
is now fixed-input determinism, which passes at exactly `0.0` for both repeat runs and
reversed input order.

---

## 6. `rerank_top_n = 5`

Selected by the **R0.5 candidate coverage audit**, evaluated on **tune + validation only**.

Rule: the smallest `N ∈ {5, 10, 20}` whose relevant-candidate coverage is not lower than
`N = 20`, required to hold for *every* audited arm. `N = 5` matched `N = 20` exactly on both
`dense` and `identifier_aware` — coverage@5 = coverage@20 = 1.0, no case lost.

**The window was not shrunk for speed; coverage evidence permitted it.** The larger window
was pure cost: it cut the provisional end-to-end p95 by 80.7% with zero coverage loss.

`rerank_top_n` is **FROZEN at 5** and was not retuned in R2 or R3. Config enforces
`rerank_top_n >= top_k`, which structurally means the tail `T` never reaches the output —
`T` exists solely to uphold the "rerank removes nothing" invariant.

## 7. Fingerprint

```
e0dedc0255c2b8a9367c331769664ec0116a85f2c4a8cacb7816a284a3356732
```

Covers provider, model name, revision, `num_labels`, `max_length`, **scored activation**,
weights manifest hash, shard count and cache schema version.

Two problems the embedding fingerprint did not handle are addressed here:

1. **Multi-shard weights.** A single `model.safetensors` assumption breaks on larger
   rerankers. Instead a deterministic **weights manifest** enumerates every weight and index
   file as `{relative_posix_path, size_bytes, sha256}`, sorted by relative POSIX path so it
   never depends on filesystem enumeration order, then hashes the canonical JSON.
2. **Activation semantics.** Recorded explicitly, so a change in score semantics invalidates
   the cache instead of corrupting it.

Cache key = `SHA256(key_algo_version + cache_schema_version + fingerprint_hash +
sha256(query) + sha256(chunk_text))`. It depends only on the model fingerprint and the exact
two UTF-8 strings fed to the reranker — **not** on threshold, `top_k`, `rerank_top_n`, batch
size, trial or collection. No API keys, no local absolute paths.

Model: `BAAI/bge-reranker-base` @ `2cfc18c9415c912f9d8155881c133215df768a70`. `rerank_model`
is in `FORBIDDEN_SEARCH_KEYS` — changing the reranker means changing the fingerprint, which
means changing the baseline. That is a version decision, not a candidate comparison.

## 8. History

| slice | outcome |
| --- | --- |
| **R0** | Activation-semantics gate PASSED · batch-invariance originally FAILED → owner fixed `batch=1`, demoted to audit evidence · fixed-input determinism gate PASSED at `0.0` · provisional budget derived |
| **R0.5** | Candidate coverage audit on tune+validation → `rerank_top_n = 5` selected with zero coverage loss · provisional p95 dropped 11,491 → 2,223 ms · split leakage disclosed |
| **R1** | `reranker.py`, `rerank_stage.py`, `rerank_cache.py`, orthogonal config fields, both strategies wired · no-rerank canonical dict verified byte-identical against git HEAD |
| **R2** | Trial-runner integration, migration `0009_rerank`, rerank telemetry, cache integration, reports · 9/9 real-Qdrant integration tests · **real end-to-end latency measured**, superseding the provisional estimate |
| **R3** | Rerank enters the optimizer search space (conditional projection, `rerank_model` forbidden) · four-arm quality comparison · deterministic gate |

A recurring pattern across R0–R2 is worth recording: **every headline number that started
as an estimate was eventually replaced by a measurement, and the estimate was wrong.** The
R0 provisional end-to-end p95 (2,222.62 ms) overstated the measured value (866.47 ms) by
about 2.6×. The provisional figure is retained only as historical contrast and is explicitly
barred from use as a gate input.

## 9. Quality result

Full evidence: [../evaluation/rerank-quality-evaluation-v1.2.1.md](../evaluation/rerank-quality-evaluation-v1.2.1.md)

**Formal (tune n=4 + validation n=5): NO MEASURABLE QUALITY IMPROVEMENT / NO
DISCRIMINATION.** Both splits are saturated — MRR, recall@1, hit@1, `exact_code_top1` all sit
at 1.0 for every arm, with or without rerank. The only moving metric, `graded_ndcg_at_5`,
shifts by at most 0.012 and in both directions.

**Descriptive (test, already inspected in R0.5): PROMISING IMPROVEMENT for
`identifier_aware+CE`.** MRR 0.80 → 1.00, hit@1 0.60 → 1.00, `exact_code_top1` 0.50 → 1.00,
`confusable_code_error_rate` 0.50 → 0.00, no case regressed. H1 and H2 both confirmed
descriptively. `dense+CE` improved less and **regressed one case** (`eval-e102-002`, rank
1 → 2).

> **Cross-Encoder reranking shows a promising ranking signal, but quality improvement is not
> formally established on the current dataset.**

Not "proved better", and not "failed". The splits that are admissible cannot measure the
effect; the split that shows the effect is no longer blind.

`identifier_aware+CE` also **inherits** the `identifier_aware` unanswerable false-positive
behaviour (`0.50` on test, unchanged by rerank). By H3 this is structurally unfixable by
reranking.

## 10. Latency result

Full evidence: [../evaluation/rerank-end-to-end-latency-v1.2.1.md](../evaluation/rerank-end-to-end-latency-v1.2.1.md)

Dedicated benchmark, n=30 per arm, warm-up timed separately, **rerank cache disabled and
verified at 0 hits**. Scope: **local native-Qdrant loopback end-to-end measurement**.

| arm | p50 (ms) | **p95 (ms)** | vs 86 ms SLO |
| --- | --- | --- | --- |
| `dense` (baseline) | 21.15 | **32.83** | 0.38× — passes |
| `dense+CE` | 491.31 | **866.47** | **10.08× — fails** |
| `identifier_aware+CE` | 557.75 | **917.36** | **10.67× — fails** |
| `identifier_aware` (no rerank) | — | **not independently benchmarked in R2** | — |

Rerank accounts for roughly 96% of end-to-end time; retrieval itself is ~4%.

> **Scope limitation:** loopback RTT is cheaper than a remote deployment and may
> underestimate remote production latency. This is not universal production latency.

**Production eligibility.** On the formal tune/validation gate, rerank candidates are
rejected by latency. Descriptive test evidence additionally shows that
`identifier_aware+CE` inherits the identifier-aware unanswerable false-positive behaviour,
which reranking is structurally unable to fix. Latency is the constraint that fires; it is
not the only production concern on the record.

## 11. Limitations

1. **Formal splits are saturated and tiny** (tune n=4, validation n=5). They cannot
   discriminate between these arms. This is the single biggest limitation of the R3 result.
2. **The test split is no longer a blind holdout** — its per-case ranks were inspected
   during the R0.5 audit. Test evidence is descriptive only.
3. **Search-internal per-trial latency is low confidence.** `latency_measurement_repetitions
   = 1`, `policy_confidence = low`, and at n=4–5 the p95 is essentially the maximum sample.
   The gate marked plain `dense` infeasible on a validation `p95 = 131.2 ms`; the dedicated
   n=30 benchmark puts dense at **32.83 ms**. **Near-threshold gate decisions from
   per-trial latency are not reliable and must not be used as engineering conclusions.**
4. **Latency scope is loopback**, single machine, CPU only, tracked demo corpus — not
   production traffic and not a cross-machine claim.
5. `identifier_aware` without rerank has **no dedicated n=30 benchmark**.
6. **Quality feasibility is `indicated, not formally established`**;
   `future_optimization_feasibility` is `not_evaluated`.
7. The search CLI's default provider **enables** the rerank cache. The committed results
   were produced with an injected provider using `rerank_cache_enabled=False`. Reproducing
   via the plain CLI yields cache-warmed latency, which is not valid feasibility evidence.

## 12. Future work

Registered only. **None of this is implemented, and none of it may be started as part of
v1.2.1.**

### A. Evaluation dataset — the blocking prerequisite

The current dataset cannot answer the question that matters:

- tune and validation are **saturated** — no headroom to detect any ranking improvement;
- the test split is **no longer pristine**, so it cannot confirm one.

A confirmatory result requires a **new, untouched, harder holdout** with cases that
actually discriminate between bi-encoder and cross-encoder ranking. Until that exists, any
further rerank tuning would be optimising against noise.

**This is the prerequisite for everything below.** Performance work on a capability whose
quality benefit is not established would be premature.

### B. Performance — only if new quality evidence justifies it

Unevaluated levers, in no particular order: ONNX Runtime, OpenVINO, quantisation, a smaller
reranker, GPU execution. None has been benchmarked; `future_optimization_feasibility`
remains `not_evaluated`. The R0 negative latency finding is scoped strictly to the current
CPU reference implementation against the current SLO and must **not** be generalised into
"Cross-Encoder rerank is universally production-infeasible".

### C. Retrieval — sparse signals

BM25 / sparse retrieval and Reciprocal Rank Fusion remain future work. They were explicitly
out of scope for v1.2.1 and were not implemented, measured, or designed.

### D. Admission-layer false positives

The `identifier_aware` unanswerable false positive is an **admission** behaviour. H3
guarantees reranking cannot fix it. If it matters, it must be addressed where it originates.
