## 1. 問題定義

v1.0 已是可運作 RAG 系統（PDF/MD/TXT 載入、chunking、BGE embedding、Qdrant、SQLite registry、vector retrieval、threshold 拒答、OpenAI-compatible LLM RAG、citation 驗證、前端、Docker Compose、evaluation script、單元/整合測試）。但已觀察到 retrieval 品質問題：

1. 查詢 `E102` 時，語意相似但代碼不同的 `D900` 暫時文件曾以較高分數搶到 Top-1。
2. 純向量搜尋對警報代碼、設備型號、欄位名稱等精確識別字不穩定。
3. Top-5 可能包含多個弱相關或高度重複的 chunk。
4. 現有 chunking 能運作，但切分粒度未必適合不同文件結構。
5. 現有 evaluation 資料量小（20 題），無法代表大量真實文件的所有查詢形式。

**根因**：retrieval 的多個參數（chunking 策略、chunk size/overlap、similarity threshold、Top-K、檢索策略）目前靠人工反覆試調；缺乏可重現、可比較、能量化「Top-5 是否合理」的機制。

**v1.1 目標**：

> 使用者只需標註少量代表性問題與正確來源範圍，系統便能自動建立不同 Retrieval 方案、執行評估、比較 Top-K 品質，找出較合理的 Chunking、Threshold、Top-K 與檢索策略，減少人工反覆調參的工作。

**定位澄清**：v1.1 核心是**可重現的 Optimizer + Human-in-the-loop 工作流**，**不是自主決策 Agent**。Agent-like 能力僅限於：LLM 產生候選問題、query type 建議、（[Optional]）Active Sampling。LLM **不得**自行產生問題後又自行判定整體系統已通過。

## 3. User Stories

- **US-1 [MVP]**：身為調校者，我想固化目前 baseline 與已知失敗案例（E102/D900），以便日後每個候選方案都能對照回歸。
- **US-2 [MVP]**：身為領域專家，我想用「原始文件來源範圍」（而非 chunk id）標註正確答案，這樣即使 chunking 改變，我的標註仍然有效。
- **US-3 [MVP]**：身為調校者，我想讓系統從文件章節產生**候選**問題並建議 query type，但由我接受/修改/刪除後才進正式 dataset。
- **US-4 [MVP]**：身為調校者，我想在**隔離索引**上自動建立多個 Retrieval Trial 並計算 metrics，過程不影響正式 RAG 服務。
- **US-5 [MVP]**：身為調校者，我想比較候選方案的 Top-5 品質（含正確結果排名、弱相關、重複、延遲），而不只看「最高分」。
- **US-6 [MVP]**：身為調校者，我想針對精確代碼查詢（E102）確保含正確代碼 evidence 者優先於僅語意相近的其他代碼。
- **US-7 [MVP]**：身為審核者，我想在 Apply 前看到 Baseline 與 Best Candidate 在相同問題下的 Top-5 差異，確認後才套用，且能回滾。
- **US-8 [Optional]**：身為調校者，我想讓系統找出候選方案間差異最大 / 最混淆的案例，主動要求我選擇正確來源，並據此重跑 optimizer。

## 4. Functional Requirements

### 4.1 Evaluation Case 管理
- **FR-1 [MVP]**：支援手動新增 evaluation case（`question` / `query_type` / `answerable` / `expected_evidence`）。
- **FR-2 [MVP]**：支援從文件章節由 LLM 產生**候選**問題並建議 `query_type`。
- **FR-3 [MVP]**：候選問題必須經人工**接受 / 修改 / 刪除**後才進入正式 evaluation dataset。
- **FR-4 [MVP]**：同一來源產生的同義問題必須放同一 `group_id`（防資料洩漏）。
- **FR-5 [MVP]**：支援 query type：`exact_code` / `semantic` / `procedure` / `cross_section` / `confusable` / `unanswerable`。
- **FR-6 [MVP]**：LLM 不得自行決定系統通過；候選題僅為建議。

### 4.2 Canonical Document 與標註
- **FR-7 [MVP]**：建立**版本化、可重現的 Canonical Document Representation**（見 §7），供 offset 對位。
- **FR-8 [MVP]**：`expected_evidence` 綁原始文件來源範圍（document + section/page/offset + anchor_text），**不綁 chunk id**。
- **FR-9 [MVP]**：`anchor_text` 為必要 fallback 欄位（非可選）。
- **FR-10 [MVP]**：`EvidenceMatcher` 支援 offset overlap、section/page match、anchor match、多 evidence span。

### 4.3 Trial 與 Optimizer
- **FR-11 [MVP]**：支援 Baseline Trial。
- **FR-12 [MVP]**：可重現的 Grid / Random Search（固定 random seed）。
- **FR-13 [MVP]**：每個 Trial 使用隔離索引 `optimizer_<run_id>_<trial_id>`，永不覆寫正式資料。
- **FR-14 [MVP]**：Trial 可中斷與恢復；Trial 失敗不得破壞其他 Trial 或正式索引。
- **FR-15 [MVP]**：每個 Trial 保存：corpus hash、dataset version、Git commit、retrieval config、`identifier_normalization_version`、metrics、latency、status、error。
- **FR-16 [MVP]**：相同文件內容 + 相同 chunk config 應盡可能重用 embedding cache，避免重算。
- **FR-17 [Future]**：Bayesian Optimization（保留介面，v1.1 不實作）。

### 4.4 檢索策略（Identifier-aware）
- **FR-18 [MVP]**：索引時從 canonical chunk text + metadata 抽取並正規化識別碼，存入獨立 payload 欄位 `identifiers`，並建 Qdrant **keyword** payload index。
- **FR-19 [MVP]**：檢索採 **candidate union**：dense candidates ∪ identifier keyword-match candidates → 依 `document_id + chunk identity` 去重 → identifier-aware reranking → final Top-K。
- **FR-20 [MVP]**：exact identifier match 加可配置 boost；含其他混淆代碼但不含查詢代碼者加 confusable penalty。
- **FR-21 [MVP]**：識別碼正規化規則必須版本化並記錄於 Trial Config，不得暗中改變。
- **FR-22 [MVP]**：query-time boost/penalty **不得**影響 embedding cache。
- **FR-23 [Future]**：完整 dense + sparse/BM25 + RRF/DBSF hybrid。Reranker（cross-encoder）亦為 [Future]。

### 4.5 Chunking 搜尋空間
- **FR-24 [MVP]**：可切換 chunking 策略：fixed token window / paragraph-aware / heading（section）-aware。
- **FR-25 [MVP]**：可調 chunk size、overlap、是否將 section title 加入 chunk、是否保留相鄰段落上下文。

### 4.6 比較、Apply、Rollback
- **FR-26 [MVP]**：候選比較須能顯示相同問題在 Baseline 與 Candidate 下的 **Top-5 實際差異**，不只顯示最佳分數。
- **FR-27 [MVP]**：Apply 前顯示 Baseline vs Best Candidate 差異並由使用者**明確確認**。
- **FR-28 [MVP]**：Apply 建立新的 versioned collection → readiness 驗證 → atomic alias switch；保留舊 collection 供 rollback。
- **FR-29 [MVP]**：Apply 請求須帶 candidate config hash；系統驗證 candidate、dataset version、corpus hash、Git commit；**stale candidate 不得套用**。
- **FR-30 [MVP]**：所有 Apply / Rollback 寫 Audit Record。
- **FR-31 [MVP]**：暫時 collection 有可追蹤清理策略。

### 4.7 介面
- **FR-32 [MVP]**：Optimizer 搜尋以 **CLI / 離線 Job** 執行；結果寫 SQLite + JSON。
- **FR-33 [MVP]**：前端新增「Retrieval Optimizer」頁，**只讀**報告並顯示比較、人工審核；Apply/Rollback 經 FastAPI 管理 endpoint。
- **FR-34 [MVP]**：前端不得直接呼叫 Qdrant。
- **FR-35 [Optional]**：Active Sampling（差異最大 / 最不確定案例挖掘、主動要求選來源、自動重跑）。
- **FR-36 [Future]**：in-process async optimizer API（前端觸發長搜尋）；獨立 worker + broker。

## 5. Non-functional Requirements

- **NFR-1 可重現**：固定 seed + 版本化（corpus / dataset / config / identifier normalization / git commit）→ 相同輸入相同結果。
- **NFR-2 隔離**：優化流程使用獨立 collection，永不觸碰 `factory_knowledge`；原始文件不可變。
- **NFR-3 不阻塞**：長時 Trial 以 CLI/離線 Job 執行，不阻塞正常 RAG API（optimizer 不在 API request 內跑長搜尋）。
- **NFR-4 非破壞 migration**：payload 新欄位對舊 point 相容（缺值為 null）；SQLite 以輕量 migration 加表，不破壞 v1.0。
- **NFR-5 效能**：拆 index-time（chunking，需重建）與 query-time（threshold/top_k/candidate/boost，同索引可掃）；embedding content-hash cache。
- **NFR-6 可觀測**：Trial 狀態、error、latency、樣本數皆可查；報告不得只給不透明總分。
- **NFR-7 相依管理**：v1.1 若新增套件，於 `pyproject.toml` 標示（現有 deps 未 pin，reproducibility 相關新增建議 pin）。
- **NFR-8 安全預設**：無人工確認不得改正式索引；不得以 LLM 自評取代人工標註。

## 6. Data / Label Schema

### 6.1 Evaluation Case（YAML 概念）
```yaml
id: eval-e102-001
group_id: grp-e102          # 同源 paraphrase 同組，防洩漏
question: 設備出現 E102 警報時應如何處理？
query_type: exact_code       # exact_code | semantic | procedure | cross_section | confusable | unanswerable
answerable: true
split: tune                  # tune | validation | test（group-aware）

expected_evidence:           # 綁原文來源範圍，非 chunk id；可多個 span
  - document: equipment_alarm_manual.md
    document_sha256: <sha256>          # 穩定 document reference
    canonical_text_version: v1         # 對位所用 canonical 版本
    section: E102 感測器通訊異常
    page: null                          # PDF 以 page-local offset；MD/TXT 可用 doc-global
    page_local_char_start: 0            # 綁版本化 normalized canonical text
    page_local_char_end: 240
    anchor_text:                        # 必要 fallback
      - E102
      - 感測器
      - 通訊異常

source_review:               # HITL 稽核軌跡
  origin: llm_candidate      # manual | llm_candidate
  accepted_by: human         # 候選題須人工接受/修改/刪除才進 dataset
```
`unanswerable` case：`answerable: false`，`expected_evidence` 可為空。

### 6.2 Canonical Document 與 Chunk payload（見 §7 與 architecture 文件）
Chunk payload 於 v1.1 新增（非破壞）：`char_start` / `char_end`（canonical 座標）、`paragraph_index`、`identifiers`（normalized，keyword index）、`canonical_text_version`、`identifier_normalization_version`。

## 7. Canonical Document Representation

Gold Label **不得**直接綁「原始 PDF 全文件 char offset」。定義版本化、可重現的 canonical 表示：

```text
document_sha256
canonical_text_version
loader_version
page
section
paragraph_index
normalized_text
page_local_char_start
page_local_char_end
anchor_text
```

規則：
1. Offset 綁在**版本化、可重現的 normalized canonical text**。
2. **PDF 優先 page-local offset**，不預設依賴全文件抽取順序。
3. Markdown / TXT 可用 document-global offset，但仍記錄 `canonical_text_version`。
4. `anchor_text` 為**必要 fallback**。
5. Loader 正規化規則改變 → 產生**新 `canonical_text_version`**。
6. Gold Label 不得靜默漂移：version 不符須顯示警示 / 觸發重新對位。
7. `EvidenceMatcher` 支援 offset overlap、section/page match、anchor match、多 span。

## 8. Metrics

### 8.1 三層 graded relevance
```text
Level 2：直接覆蓋 Gold evidence span
Level 1：同一正確 section/page，且提供有用上下文
Level 0：不相關或混淆來源
```
若標註不足以支援 graded relevance，**NDCG 標示「不可計算」，不得硬算**。

### 8.2 Metrics 清單
```text
Evidence Hit/Recall@1/3/5
MRR
Graded NDCG@5           （標註足夠時；否則標不可計算）
Evidence Coverage@5
Relevant Section Precision@5   （= section/evidence relevance precision，非單一 chunk id 判斷）
Exact-code Top-1 Accuracy
Confusable-code Error Rate
Unanswerable False-positive Rate
Duplicate/Near-duplicate Ratio
P50/P95 Latency
Index Size
Trial Build Time
```

### 8.3 Near-duplicate 判定草案
```text
相同 evidence group / 高度文字重疊 / 相同 document+section 且內容高相似
```
**Optimizer 不得為降低 duplicate ratio 而移除必要的跨段（cross-section）答案。**

### 8.4 「合理 Top-5」選擇法（不用單一相似度）
1. **硬限制**（可配置，預設 **[TODO:Slice0]** 由 baseline 推導）：
   - exact-code accuracy ≥ 門檻
   - unanswerable false-positive rate ≤ 門檻
   - P95 latency ≤ 門檻
   - semantic Recall@5 不得低於 baseline − ε（防退化）
2. 通過限制者依 **MRR → Relevant Section Precision@5 → Recall@5** 排序。
3. 同時輸出 **Pareto Frontier**，不只給不透明總分。

### 8.5 Exact-code vs Semantic 排序策略
**不同策略**。查詢偵測到識別碼 → identifier-aware path（candidate union + boost + confusable penalty）；否則 semantic path。策略選擇可作為 trial 維度。

### 8.6 資料切分（防過擬合）
- `tune`（搜尋參數）/ `validation`（選候選 + 早停）/ `test`（最終驗收，不參與搜尋）。
- **group-aware**：同 `group_id` 整組進同一 split。
- 小型作品集**不硬寫 60/20/20**；優先確保 test 覆蓋 `exact_code` / `confusable` / `unanswerable`。
- 記錄各指標樣本數與不確定性；樣本太小時報告標註，不宣稱數字必然合理。

## 9. Safety Rules

- 原始文件不可變；每 Trial 隔離索引，永不覆寫 `factory_knowledge`。
- 未經人工確認，Agent 不得：改原始文件、覆寫正式 collection、刪正式 points、改 evaluation test set、部署未驗證設定。
- Apply 走 alias atomic switch；Apply 後**不得立即刪舊 collection**（保留 rollback）。
- 不得直接 rename collection 當 rollback；不得無 readiness 驗證即切 alias；Trial collection 不得被誤設為正式 alias。
- Stale candidate（config hash / corpus / dataset / commit 不符）不得套用。
- 所有 Apply / Rollback 寫 Audit Record。
- LLM 產生候選題僅為建議，不得自評通過。
- v1.1 不含登入 / RBAC；**須明載「目前為單機作品集管理介面」為安全限制**（多人 / 生產部署需另加驗證與權限）。

## 12. 十個設計問題的明確回答

1. **使用者最少需標註什麼才足以比較不同 chunking？**
   每個代表性 case：`question` + `query_type` + `answerable` + `expected_evidence`（document + 至少一個定位子 section/page/offset + `anchor_text`）。因為 relevance 判定綁原文來源範圍而非 chunk 邊界，這已足以跨不同 chunking 比較。
2. **如何讓 Gold Label 不受 chunk 邊界改變影響？**
   relevance 用 evidence-span overlap / section-page / anchor 判定，綁**版本化 canonical 座標**；chunk 邊界改變不影響 gold。anchor_text 為 offset 缺失時的 fallback。
3. **Top-5「合理」如何量化？**
   三層 graded relevance + §8.2 metrics；選擇法為「硬限制 → MRR/Precision@5/Recall@5 排序 → Pareto」，不用單一相似度、不用不透明總分。
4. **Exact-code 與一般 semantic 是否用相同排序策略？**
   **不同**。exact-code 走 identifier-aware candidate union + boost/penalty；semantic 走 dense path。策略可作為 trial 維度。
5. **Hybrid Search 最小可行實作？**
   Identifier-aware candidate union：dense candidates ∪ `identifiers` keyword-match candidates → 去重 → boost/penalty → Top-K。不是完整 BM25；full-text index 僅作一般 match/filter，識別碼用 keyword index 精確比對。完整 sparse hybrid 為 [Future]。
6. **是否需要獨立 Optimizer Worker？**
   **v1.1 不需要**。CLI/離線 Job + 前端只讀報告；不加 worker/broker。之後若要前端觸發，再加 in-process async（仍不加 broker）為 [Future]。
7. **如何避免每個 Trial 重算所有 Embedding？**
   拆 index-time / query-time 參數（query-time 同索引可掃不重建）；chunking trial 加 content-hash embedding cache；相同 `(corpus_hash, chunk_config)` 索引可重用。query-time boost 不影響 cache。
8. **如何防止對少量 evaluation cases 過擬合？**
   tune/validation/test group-aware split；test 不參與搜尋；硬限制擋退化；記錄樣本數與不確定性；小樣本不宣稱數字必然合理。
