## 2. Locked design decisions（已定案,不得再議）

| 項目 | 決定 |
| --- | --- |
| `rerank_strategy` | `none` \| `cross_encoder`（二元 arm,無中間態） |
| `rerank_top_n` | **5**（由 R0.5 coverage audit 選出,見 §5.1）;**必須 `>= top_k`** |
| `rerank_weight` | **不存在** —— cosine 與 cross-encoder 分數未經校準,線性加權無可比較意義 |
| Primary ranking score | **raw Cross-Encoder logit**（`ranking_score = rerank_score`） |
| `rerank_score_normalized` | `sigmoid(logit)`,**僅供 report / audit**,不作排序鍵或 tie-break 鍵 |
| Tie-break | **完全不動**;raw score 相等時落入既有 5 鍵 deterministic chain |
| `vector_score` | 永遠保留 RAW cosine,不被覆寫 |
| Rerank filtering | **禁止**;rerank 無 admission / filtering 權限 |
| Admission | 保持在 rerank **之前**,以 raw `vector_score` 判定,邏輯未改 |
| `RERANK_BATCH_SIZE` | **固定 = 1**（見 §4 remediation）。runtime 常數,**不進** `RetrievalConfig` / config hash / cache key / search space |
| Production | 維持 **dense-only**,本版本不接 rerank |

### 2.1 Rerank window 語義（W / T）

設 `A` = admission 後、依既有 deterministic ranking key 排序的候選序列。

```
W = A[:rerank_top_n]     -> 送進 cross-encoder,依 raw logit 重排
T = A[rerank_top_n:]     -> 不丟棄,維持原相對順序,接在 rerank(W) 之後
輸出 = (rerank(W) ++ T)[:top_k]
```

- `rerank_applied` 逐筆標記:W 內 `true`,T 內 `false`。
- 因 `rerank_top_n >= top_k`,`|A| > rerank_top_n` 時最終 top_k 全來自 W;
  T 存在的目的是維持「**任何候選都不會被 rerank 移除**」的不變量。

### 2.2 H3 安全不變量（精確敘述）

> rerank stage **不具備 admission 或 filtering 權限**。
> 對任一 case:`results` 為空 ⟺ admitted set `A` 為空。

依據:`evaluation/v11/retrieval_metrics.py:205` 與 `:583-586` ——
`unanswerable_false_positive` 只判定「回傳清單是否為空」,與 relevance / 排序 / 分數無關。
故 A 非空 ⇒ W 非空 ⇒ 輸出非空,FP rate 結構性恆等。
**一旦加入任何 rerank 分數門檻,H3 立刻失效** —— 此禁令不可移除。

### 2.3 identifier-aware 訊號的實際保留範圍（措辭規範）

| 層 | cross_encoder 啟用後 |
| --- | --- |
| candidate pool / admission | **保留**（union 與 `identifier_vector_floor` 未改動） |
| rerank window membership | **保留**（`\|A\| > rerank_top_n` 時,A 的順序由既有 identifier ranking 決定） |
| **window 內** primary ordering | **改由 cross-encoder 決定**（boost/penalty 的排序貢獻在此喪失） |
| tie-break | 形式上保留,實務影響趨近於零 |

**不得**描述成「identifier ranking 影響完全消失」。cross-encoder 接管的是 **window 內的 ordering**。

## 4. R0 實測發現

### GATE 1 — Activation semantics：**PASSED**

```
num_labels = 1 · CrossEncoder 預設 activation = Sigmoid · 本專案採用 = Identity
raw score 範圍 = [-10.1967, 3.5685]   (落在 [0,1] 外 -> 確為 logit)
sigmoid(raw) vs 預設輸出 delta = 0.000e+00   (確認為 sigmoid 關係)
```

> **必須顯式處理的陷阱**:`predict(activation_fn=None)` 會套 `model.activation_fn`,
> `num_labels=1` 時預設 `torch.nn.Sigmoid`。不顯式傳 `torch.nn.Identity()` 的話,
> raw-logit 主鍵設計會**靜默失效且無錯誤訊號**。`CrossEncoderReranker` 必須永遠顯式傳 Identity。

### GATE 2 — 跨 batch invariance：原門檻 **FAILED**（owner 已裁示 remediation）

32 組固定真實 pair（token 長度 33–312）,原 tolerance `1e-6`:

| 比較 | max_abs_delta | mean | 非零 pair |
| --- | --- | --- | --- |
| b1 vs b8 | **4.292e-06** | 6.59e-07 | 14/32 |
| b1 vs b32 | 3.874e-06 | 7.47e-07 | 13/32 |

**成因已定位**:

| 對照 | 結果 | 推論 |
| --- | --- | --- |
| 完全相同輸入（無 padding 差異）b1 vs b8 | `0.000e+00` | 偏差**來自 padding** |
| 同 batch size 連跑兩次 | b1/b8/b32 皆 `0.000e+00` | 固定組成下**完全 deterministic** |
| float32 ULP @ max\|score\|=10.1969 | `1.216e-06` | 偏差約 **3.5× ULP**,累加順序固有變異 |

兩次獨立執行的 `max_abs_delta` 皆為 `4.292e-06`(bit-stable)→ padding 形狀改變
reduction order 的**確定性**後果,不是隨機抖動。

各 batch size 成本（CPU;變長輸入會 padding 到批內最長,大 batch 反而浪費算力）:

| batch | 1 | 8 | 16 | 32 |
| --- | --- | --- | --- | --- |
| ms/pair | **218.96** | 225.82 | 259.51 | 404.75 |

### Repository Owner remediation decision

**固定 `RERANK_BATCH_SIZE = 1`。** 理由:

1. batch=1 定義上無 padding → padding-induced delta 為 **0**
2. fixed composition 下已證實 deterministic
3. batch=1（218.96 ms/pair）比原訂 batch=16（259.51 ms/pair）**更快**
4. 因此 batch size 維持 runtime constant,**不進** `RetrievalConfig` / config hash /
   cache key / optimizer search space

**跨 batch 的 `<=1e-6` gate 不再是阻塞條件**（batch 已非可變參數）。
原 batch 1/8/32 實驗結果**保留為 audit evidence**,說明「為何固定 batch=1」。
**保留 fixed-input deterministic regression check 作為阻塞檢查。**

## 8.1 Future work（**只登記,不實作**）

完整敘述見 [`docs/v1.2.1-rerank-design.md` § 12](v1.2.1-rerank-design.md#12-future-work)。

「current CPU reference implementation × 目前 SLO」,**不得**泛化為
「Cross-Encoder rerank 普遍不可行」。

**C. Retrieval**

BM25 / sparse / RRF 仍為 future work。

**D. Admission-layer false positives**

`identifier_aware` 的 unanswerable FP 屬 **admission** 行為,H3 保證 rerank 無法修正;
若要處理必須在其發生處（admission）處理。
